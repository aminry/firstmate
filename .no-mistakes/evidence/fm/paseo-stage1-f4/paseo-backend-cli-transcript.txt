 8. Endpoint-record safety, exercised through a real CLI (fm-control.sh),
    reading the persisted state/<id>.meta a task cleanup would act on.
    Paseo terminal ids are opaque UUIDs that do not encode the task label, so
    the endpoint_task_id binding is the ONLY thing tying a record to its task,
    and window= is cross-checked against its two recorded parts. Every wrong
    record must REFUSE and say it is preserving task state, because the
    caller's very next step is destructive teardown.
===============================================================================

--- a well-formed paseo record: validation PASSES (control then stops later,
--- on paseo having no control adapter - which is exactly the point) ---
$ fm-control.sh paseo-good interrupt
error: harness claude interrupts with Escape, which the paseo backend cannot deliver; refusing to send a different key

--- a truncated record, missing paseo_terminal_id ---
$ fm-control.sh paseo-truncated interrupt
REFUSED: paseo endpoint metadata for task paseo-truncated is malformed or inconsistent; preserving task state.

--- window= disagrees with the recorded parts (hand-edited/truncated) ---
$ fm-control.sh paseo-mismatch interrupt
REFUSED: paseo endpoint metadata for task paseo-mismatch is malformed or inconsistent; preserving task state.

--- the record is bound to a DIFFERENT task ---
$ fm-control.sh paseo-foreign interrupt
REFUSED: endpoint metadata belongs to task some-other-task, not paseo-foreign; preserving task state.

--- a terminal id carrying shell metacharacters ---
$ fm-control.sh paseo-unsafe interrupt
REFUSED: paseo endpoint metadata for task paseo-unsafe is malformed or inconsistent; preserving task state.

  -> Every wrong record refuses and says "preserving task state". Every decision
     above is made from durable metadata alone: no Paseo daemon is contacted, so
     a down daemon can never turn a valid cleanup record into a refusal, or the
     reverse.
